## Goal and reason

Until this block, every movement of a cover is invisible to the integration: the walking skeleton (M1) records what it would have sent and judges the next decision against the reported position, but it cannot say whether the integration moved the shutter or somebody else did. That question is the heart of E1 to E3 and of guardrail 6: a movement the integration did not command makes the comfort logic leave the window alone, and a movement it did command must never be mistaken for a person at the window. Without a tracker no dam is ever armed, a stalled actuator is never noticed (N1), and the pilot can compare decisions but never sees a foreign movement in the window's own status. This block builds the tracker, the arming and ending of the two dams, and the bookkeeping the arbiter needs from real movements. It is a safety-relevant core block: what it attributes wrongly either freezes the automation or overrules a person.

## Scope

The items are ordered. The first one is a ruling of the project owner and is built before anything else.

1. **The core names the commanded members itself.** A decision whose gate outcome is `send` states, per target, whether the member is addressed: it has a target and is available, and it does not stand at that target within its own tolerance; a member without position feedback cannot be judged and is addressed. Gate rules 2 and 3 already reason in these "addressed members"; this block makes that one function of the core, read by the gate, by `Engine.state_after_send` (which then records the addressed members and nothing else), by the runtime and by the simulation runner. The interim filter of the runtime controller (`_targets_to_send`) is deleted and the runtime reads the decision, in this block, with its test; the simulation runner reads it too. Two rulings of the project owner belong to this item, with the reasons in the C06 row of `TASKS.md`; counter-arguments are welcome, stated in the pull request before the item is built, not after:
   - **The return of a member that was unavailable during a command is the completion of that command, not a fresh wish.** Only the returning member is addressed, with the class and the reason of the command the others received; it counts no comfort movement for the daily count and it is not subject to the minimum interval, because the wish was fresh when the command was given.
   - **A send addresses only the members that do not stand at the target within tolerance.** A member that already stands there gets no command and no record.
2. **Normalizing reports** (section 8.2). The runtime already reduces a Home Assistant state to an `Observation` (`members.py`); the core receives observations, never states. The tracker drops an observation that does not change what it knows: an identical write, an attribute-only write that precedes the resting state by milliseconds, a rewrite of an unchanged state with a new change time. A decision is never based on a change time.
3. **The tracker per member** (section 8.3, module `tracking`): `idle` → `expecting` → `moving` → `settling` → `idle`. Own commands are already recorded by `Engine.state_after_send` and `Engine.on_command_result`; this block adds what the record lacks for tracking, with optional keys within schema version 1, as block H03 did for `failed`. The deadline comes from `member_expectation_end` (see "Verify before you build"). A movement is evaluated once, a settle time (default 2 s) after the resting observation: within tolerance of the target it is the own movement and the expectation is consumed; outside it somebody intervened. The tolerance follows the position source of the member (2 for `calculated`, 3 for `measured`, minimum 1); the position source is a per-member value of the capability profile with the default `calculated`, and this block puts it into the settings registry of the core so that block H10 can build its form. Reversal during `expecting` or `moving` is external at once. A member with a report delay expects no transit state and is evaluated at the first resting report after the command or at the deadline. No reaction by the deadline is `actuator_no_reaction`; a movement that started but did not come to rest by the deadline is `movement_not_finished`; both go to command verification (block H15) and never arm a dam. A movement that starts in `idle` is external. An unavailable gap that ends with the same observation is nothing; with a different position it is `moved_during_downtime` and counts as external. A user ID in the context of a report shortly after a foreign command is recorded as a hint for the diagnostics and never decides (guardrail 6). Glass calibration never enters the comparison.
4. **The window-level view over the members** (section 9). The window is moving from the first member that moves until the last one has settled. One member moved by hand is a hand movement of the whole window (decision 8): the override applies to the window, the other members stay where they are, and the events `manual_detected` (the window) and `manual_detected_member` (which member) are both raised. The statements "position" and "all members at their commanded targets" exist since C01 and are not changed here.
5. **Arming and ending the two dams** (section 3, module `dams`). An external movement while no protection wish is winning arms the manual override dam with the position the person chose and sets the owner of the position to `user`. An external movement while a protection wish is winning arms the person-at-the-window dam. The arming reads the winning wish class of the decision, so block C07, which brings the protection layers, changes nothing here; the tests use a stub protection layer as C05 used a stub fire trigger. The end rules of E2: after fixed minutes; when the shading episode ends, only if the dam was armed during one (the episode state exists, block C10 fills it); at the next boundary between parts of the day (the default; the schedule of C04 knows the boundaries); after the room has been empty for the configured time (a presence source on the window's snapshot, optional, read like every other source); and at once through `Engine.resume`, the function the "resume automation" button (H06) and the action (H07) call. Switching sleep mode on ends the dam; this block provides the function, block C11 calls it. The person-at-the-window dam ends by itself after the configured time (default 15 minutes) and, if the protection event has ended in the meantime, turns into a manual override dam with the person's position (section 3.2). During an active protection event the clock of the override keeps running (decision 4). Every arming and every end raises its event (`override_started`, `override_ended`, `person_at_window_started`, `person_at_window_ended`). In dry-run no dam is ever armed: a foreign movement raises `external_movement_observed` and nothing else, so that a window next to a second controller shows a clean record (section 2.3). The settings of the end rules and durations go into the registry with fault values under the rules of section 13a; state in the pull request which function they belong to and what their cautious values are (see the open questions).
6. **The position reference flag and its hint** (section 8.4). The flag becomes `uncertain` after a movement that was stopped from outside, after `movement_not_finished` and after `moved_during_downtime`; the frost cases are calls that the blocks C10 and C11 make. It becomes `referenced` again by any complete movement into an end position, whoever commanded it. When it turns `uncertain`, the event `position_may_be_inaccurate` is raised once. Members without `set position` and members without position feedback keep `referenced`. The flag changes no decision.
7. **The daily count of comfort movements** (E10, gate rule 9). The count of own comfort movements per window and local day, with its date, and whether the threshold was reported: a movement counts when it is sent as comfort; a take-over counts nothing (`docs/dev/arbiter.md`); protection and fire never count; the completion of a command for a returning member (item 1) counts nothing. Above the threshold (default 40, a setting of the registry) one event per day with a new reason code. The project owner ruled in the C06 row of `TASKS.md` that this code is added to section 5 of the specification together with its enumeration entry and both translations; this block makes that change to `docs/architecture.md` and names the code in the pull request (proposal in the open questions).
8. **The tracker measures itself** (section 8.3, last paragraphs). Per member and own movement: the latency from the command to the first report, the time to the resting report, and the deviation between the commanded and the reported end position; the last values and count, median and maximum. Nothing is tuned from them.
9. **The engine façade.** `Engine.observe(state, member, observation, now, last_decision)` returns the state after an observation and the events it raised; `Engine.resume(state)` ends the override; the wake-up times a caller has to arm (settle time, expectation deadlines, the end of a dam) come from one function next to `member_expectation_end`, so that the runtime and the simulation never compute a time of their own. Every function stays a pure function of its arguments.
10. **Simulation scenarios** (`tests/sim/scenarios.py`), each against the record and the assertions of C05: every cover behaviour profile with an own movement, a hand movement, a stop in mid-travel, a dropout with the same and with another position, and a reversal; the polled platform with four members commanded at once; the blocked curtain with a calculated position; the two-member window with one member moved by hand (decision 8); each end rule of the override; the person-at-the-window dam under a stub protection event, ending before and after the event; a window in dry-run next to a scripted second controller for a whole day (no dam, one event per foreign movement); a restart during a movement and during an armed dam; the year scenario with a scripted hand movement per window and day. The pin test of C05, `test_a_cover_that_settles_beyond_its_tolerance_is_sent_every_interval`, stays as it is unless the tracker changes its outcome; if it does, say why in the pull request.

## Acceptance criteria

- The decision names the addressed members; `Engine.state_after_send` records exactly those; the runtime controller and the simulation runner contain no filter of their own, shown by a test on each side. A member that returns from unavailable is addressed alone, with the class and reason of the pending command, counts no comfort movement and passes the minimum interval.
- For every cover behaviour profile of the simulation: an own command to a target is attributed to the integration and arms no dam; a hand movement arms the override with the person's position; a stop in mid-travel is external and turns the reference flag `uncertain`; a dropout that ends in the same observation changes nothing, one that ends with another position reads `moved_during_downtime`.
- A reversal during an own movement is external before the movement ends.
- On the polled platform with four members commanded at once, no false manual detection and no `actuator_no_reaction` for a member that reported within its deadline.
- `actuator_no_reaction` and `movement_not_finished` never arm a dam and never change the owner of the position.
- A window in dry-run next to a second controller for a whole day arms no dam, keeps the owner `unknown`, and raises exactly one `external_movement_observed` per foreign movement.
- Each end rule of the override ends it at the right instant, with `override_ended`; `Engine.resume` and switching sleep mode on end it at once; during an active protection event the clock keeps running and the remembered position is restored only if the dam is still armed when the return is due (decision 4; tested with a stub protection layer and a stub return wish).
- The person-at-the-window dam is armed only while a protection wish is winning, holds protection and comfort back and never fire, ends after its time, and turns into an override if the event has ended.
- One member moved by hand arms the override for the whole window; the other members are not commanded while it holds; when it ends, all members are brought to their targets.
- The daily count counts comfort sends only, once per take-over chain, resets at the local day change, and raises its event once per day above the threshold.
- A restart of the simulation during a movement, during a settle time and during an armed dam yields the same subsequent commands and events as the uninterrupted run; no false manual detection and no duplicate command after the restart.
- The year scenario with a hand movement per window and day shows no command loop, and no own movement ever arms a dam, checked by an assertion of the record.
- Every wake-up time a caller needs comes from the core; the simulation runner asks for no time of its own.
- The purity proof, the fault-value tests, the layer trigger test and the translation completeness test pass unchanged; coverage of `core/` stays at 100 %.

## Open questions

None blocks the start; each has a recommendation, and the project owner answers in the pull request or before.

1. **The deadline formula.** If `member_expectation_end` differs from section 8.3 (see "Verify before you build"): implement the specification's formula in that function. *Rejected:* a second function for the tracker, which would give the gate and the tracker different deadlines for the same command.
2. **Is the self-measurement persisted?** Recommendation: yes, with the member state, bounded to the last twenty samples per value, and section 11 of the specification names it; a restart that erases the only numbers a user has for the report delay and the travel times would make tuning a polled platform hard. *Rejected:* in memory only, as section 11 reads today.
3. **The reason code of the count threshold.** Proposal: `comfort_movements_threshold`, group "tracker and life cycle (events only)", with the count and the threshold as attributes of the event.
4. **Fault values of the new settings.** Recommendation: the settings of the override (end rule, minutes, empty-room minutes) and of the person-at-the-window dam (duration) belong to the function `manual_override`, which falls back (it restricts movement); cautious values: the end rule `next_part_of_day`, the durations their defaults, so that a faulty setting never lets the automation overrule a person earlier than the default would. The position source and the tolerance are values of the capability profile and have no fault value: a faulty stored source is read as `calculated`, the cautious default.
