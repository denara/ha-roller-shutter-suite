## Goal and reason

The integration exists first of all to keep a house safe when the weather turns and to open every escape route when a smoke detector fires (goals G1 and G2 of the brief; D1 to D9). Until this block the arbiter knows the classes fire and protection, the fire bypass and the sleep-room exception, but the two layers that create such wishes are stubs of the simulation: no source triggers an event, no event ends, nothing returns a window to where a person had put it, and no watchdog releases an event that hangs. This block builds the fire layer, the protection layer with its events, the return after an event, and the watchdog, so that block H08 can wire real sources to them. It is a safety-relevant core block: a wrong direction, a missed end or a wrong return moves a shutter into the wind or keeps an escape route closed.

## Scope

1. **The fire layer** (section 2.1, layer 1; section 2.4). One fire source of the house, binary. While the alarm is active: open fully, class fire, reason `fire_alarm`, every member, no intermediate target. When the alarm has ended and nobody has acknowledged it: "leave alone" with `fire_unacknowledged`, which still wins and holds every lower layer back. `Engine.acknowledge_fire(state)` clears the flag (`fire_unacknowledged` in the state) and raises `fire_acknowledged`; block H07 calls it from its action and block H14 from a button. A source that is unavailable or unknown changes nothing: an active alarm stays active, an inactive one stays inactive (D6). The fire event of the Home Assistant layer (H04 fires the reason event) is fired at once also under maintenance lock and in dry-run, because the decision names the fire wish as the winner in both cases (`docs/dev/arbiter.md`); this block does not change that, it tests it with the real layer. Not for fire: the watchdog, the return, the sleep-room exception, staggering, frost.
2. **Protection events** (section 10.1). Each event: a trigger source (binary; a list of states; or a number with a threshold, with hysteresis if the settings registry already has a threshold type, see `schedule_brightness_threshold`), a direction (open or closed), a unique rank, a waiting time after its end (default 30 minutes), a maximum duration for the watchdog (default 12 hours, 0 disables), and per window the sleep-room exception. The trigger has three states: active, inactive, unknown; unknown changes nothing (D6). The state of each event is persisted (`ProtectionEventState`); after a restart an event whose source is unavailable stays what it was, and an event whose source reports active at start becomes active (caught up; the reconciliation itself is C12's, this block provides the pure function that judges a persisted event against a live source). Several active events: the highest rank wins, ranks are unique and the registry refuses a duplicate. The wish is the end position of the direction, class protection, reason `protection_event` with the event as a separate attribute of the decision, never inside the code. Constraint 7 ("no intermediate position during a protection event") and constraint 2 (the sleep-room exception) exist since C03; this block makes them read the real events and tests situations 4 to 6 with them. Events `protection_started` and `protection_ended` on each change.
3. **The blind source** (section 10.1, "A blind protection must not stay silent"). While a trigger source has been unavailable or unknown for longer than the configured time (default 1 hour, a setting of the house), the layer reports `input_held_last_known` with the event and the source, and raises `protection_source_blind` once per blind phase; the repair issue is block H08's. The behaviour of the event does not change. The same clock exists for the blocking contact of lockout protection (`lockout_contact_blind`); whether that belongs to this block or to C08 is an open question below.
4. **The return after an event** (section 10.2, decision 14). When an event starts, the window remembers its position and the owner of that position (`remembered_position`, `remembered_owner` exist in `ProtectionEventState`). When the event has ended (or was released) and its waiting time has passed without a new activation: if the remembered owner was `user` and the manual override dam is still armed, the layer expresses a wish of class comfort with the reason `protection_return_manual` and the remembered position; the dam lets exactly this wish pass (the mechanism exists since C03). Otherwise there is no return wish and the window is recomputed normally. The four conditions of decision 14 are each a test: (a) the override must still be armed, (b) the person-at-the-window dam holds the return back, (c) every constraint applies to it, (d) the waiting time has passed. A remembered position that is unknown is skipped. The waiting time runs from `return_clock_start` (the release if there was one, otherwise the end); it is configuration and is applied when evaluated, so a changed setting takes effect at once (section 11). The wake-up time for the end of the waiting time comes from the core, next to the other wake-up times of C06.
5. **The watchdog** (section 10.3, decision 10). An event active longer than its maximum duration is released for this activation: `released_at` is set, its layer has no opinion any more (`watchdog_released`), the return of item 4 runs, and the event `watchdog_released` is raised (the repair issue is H08's). The release lasts until the trigger has been genuinely inactive once; a source that is unavailable does not end the release; only a new activation makes the event effective again. Not for fire. The maximum duration 0 disables the watchdog for that event.
6. **The person-at-the-window dam under a real protection wish.** C06 arms the dam when an external movement is observed while a protection wish is winning, with a stub layer. This block replaces the stub in the scenarios with the real layer and tests situation 7 (a wall button during storm, then 15 minutes pass: the storm position is restored and a reason event is fired) and situation 8 (an override active when a storm begins: the window closes, the dam stays armed with the person's position).
7. **Fault values** (section 13a). Both functions fall back. Cautious values, to be stated in the pull request with their reason: a faulty direction skips the event on that level (no cautious direction exists: "open" is right for hail on some curtains and wrong on others, section 6 of the brief); a faulty rank makes the event lose against every valid one; a faulty waiting time is the default; a faulty maximum duration is the default, never 0 (a fault must not switch the watchdog off); a faulty blind time is the default. A faulty sleep-room exception on a window is "no exception" for that window (protection wins over sleep).
8. **The engine façade.** `Engine.acknowledge_fire`, the wake-up times of the waiting time and the watchdog, and the pure function for judging a persisted event against a live source (for C12). The simulation runner drives the real layers; the two stubs of `tests/sim/stubs.py` are deleted, and every existing scenario that used them (`fire-automatic` and the others) runs against the real layers with the same outcome.
9. **Simulation scenarios**: situations 1 to 10 and 14 of section 4 as named scenarios; the storm of C05's `storm` scenario against the real layer (never an intermediate position, also with a door that opens during the storm); a storm with a source that drops out and returns (D6); the watchdog releasing a stuck source and re-arming after one inactive report; two events at once with different ranks and directions; a fire during a storm (fire wins, unstaggered, and after the acknowledgement the storm wish applies again); the fire that ends without acknowledgement while somebody closes a shutter by hand (nothing reopens); a restart during an active event and during the waiting time (same subsequent commands).

## Acceptance criteria

- Situations 1 to 10 and 14 of section 4 of the specification run as scenarios and yield exactly the reason codes the table names.
- Fire opens at once and unstaggered in every operating mode and skips every rule and constraint of the bypass; under maintenance lock and in dry-run nothing moves and the decision names the fire wish as the winner; after the alarm ends nothing moves until the acknowledgement, a hand movement in that phase arms the override and is not undone after the acknowledgement.
- An event's trigger follows active, inactive and unknown exactly as section 10.1 says; a source that is away for longer than the blind time yields the blind event once and changes no behaviour.
- The return after an event happens if and only if the four conditions of decision 14 hold, one test per condition; the waiting time follows a changed setting without a restart.
- The watchdog releases after the maximum duration, not for fire, not with the duration 0, and re-arms only after one genuinely inactive report.
- Two events active at once: the higher rank wins; a duplicate rank is refused by the registry with a fault, never at runtime.
- The fault values of item 7 hold and never loosen a protection (the two generic fault-value tests of `docs/dev/arbiter.md` cover the new settings).
- A restart during an active event, during the waiting time and during a release yields the same subsequent commands as the uninterrupted run.
- The two stubs are deleted and no scenario of C05 changed its outcome.
- Purity proof, fault-value tests, layer trigger test and translation completeness pass; coverage of `core/` stays at 100 %.

## Open questions

None blocks the start; each has a recommendation, and the project owner answers in the pull request or before.

1. **Where does the blind clock of the lockout contact live?** Recommendation: in this block, as one generic "source blind" clock that both the protection layer and, from C08 on, the lockout constraint use; the code is the same and the repair issues of H08 read one shape. *Rejected:* two clocks in two blocks.
2. **The number-with-threshold trigger.** Recommendation: threshold and hysteresis as the existing threshold type of the registry (`schedule_brightness_threshold`), active above the threshold by default with an "invert" switch, so that a wind speed and a "calm" sensor both work. *Rejected:* a threshold without hysteresis, which would flap at the value.
3. **The external request layer** (layer 4 of section 2.1: a requested position with a reason and an expiry; `ExternalRequest` exists in the state). It belongs to C11 by the index, but block H07 in this wave needs it for "request position with reason" and for the reference run. Recommendation: build it here as the last item, it is small (a wish of class comfort from the persisted request until it expires or is cleared, decision 2 on its place below sleep mode), with `Engine.request(state, position, reason, expires)` and `Engine.clear_request(state)`, and the C11 row loses it. *Rejected:* H07 shipping two actions that only store a request nobody reads; reordering the waves.
4. **Reason for an event in the decision.** Recommendation: the decision carries the event identifier and the source as attributes next to `protection_event`; the status of H04 shows the translated name of the event. *Rejected:* one reason code per event, which section 5 forbids.
